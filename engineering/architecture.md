# Architecture

## Shape

```
docs/*/*.md and shared/seed/facts.json ──▶ seed scripts (server) ──▶ kb_source, kb_version, kb_chunk, kb_fact ──▶ /api/kb/site
client/src/data/*.json ──zod parse──▶ client/src/data/index.ts ──▶ components and pages
/api/kb/site ──▶ client/src/lib/kbStore.ts (KbGate) ──▶ setFacts / setDocs ──▶ client/src/data/facts.ts (rateBp, cents, count) and client/src/content/docs.ts ──▶ engines' inputs, FactValue badges, pages
shared/src/utils/*.ts and client/src/utils/*.ts (pure engines) ◀── components pass numbers in, render numbers out
localStorage ◀──▶ client/src/utils/progress.ts ◀──▶ client/src/progress/ProgressContext.tsx

browser ──/api (Vite proxy to :5191 in dev)──▶ Express (server/src/app.ts)
   ├─ /api/health  ──▶ { ok }
   ├─ /api/meta    ──▶ { region, otherRegionUrl, legalVersion } (no session, no database; Stage 3)
   ├─ /api/auth/*  ──▶ Better Auth (users, sessions, workspaces = organizations)
   ├─ /api/clients ──▶ requireFirm ──▶ clientService ──▶ withOrg(orgId, …) ──▶ Postgres as chub_app (RLS)
   ├─ /api/clients/:clientId/ledger, /reports ─▶ requireFirm ──▶ ledgerService ──▶ withOrg ──▶ @chub/shared utils (csv, ledgerImport, reports)
   ├─ /api/conversations (incl. POST /:id/messages as SSE), /api/chat/status ─▶ requireFirm ──▶ conversationService / chatService ──▶ redact ──▶ searchKbForChat ──▶ ChatProvider (Anthropic, Gemini); usageService ──▶ ai_usage
   ├─ /api/clients/:clientId/documents ─▶ requireFirm ──▶ documentService ──▶ withOrg ──▶ documents/extract, privacy/crypto (sealed bytea)
   ├─ /api/kb ───────▶ no session ──▶ kbPublicService (published versions only; facts)
   ├─ /api/admin/facts ▶ requireAdmin ──▶ factService ──▶ kbService (re-chunk) (global tables)
   ├─ /api/admin ────▶ requireAdmin (404 for anyone else) ──▶ adminUserService, auditService (global tables)
   ├─ /api/admin/kb ─▶ requireAdmin ──▶ kbService ──▶ kb/ (chunk, validate, diff, retrieve) ──▶ ai/embed (Gemini, optional)
   ├─ also /api/clients/:clientId/{requests,request-links,engagements}, /api/public/requests (no session), /api/engagements, /api/engagement-templates, /api/workload, /api/audit, /api/workspace (see Folders, routes)
   └─ any other GET, only when WEB_DIST_DIR is set (P5d image) ──▶ client/dist (index.html fallback; never for /api)
```

The practice data (quizzes, flashcards, scenarios) is bundled at build time; the curriculum and the facts are not (see "Facts and guides in the database"). The API (`server/`) holds accounts, firms, client headings, the platform admin and the knowledge base (P2a); a firm can import a client's trial balance as CSV and read a profit and loss and a balance sheet from it (D1); facts and guides are edited in the admin and read by the web from the API (P2b), and the grounded, cited chat with rules-only redaction and a minimal spend guard is built (P3, live provider check owed); an entity's documents, kept sealed and attachable to its chat as context, and a sealed placeholder map per conversation are built (P4, live check owed); rate limits, email, the audit log and retention, and the deploy image with backups and key rotation are built (P5a to P5d). The main chunk carries the practice data; each other page is a lazy chunk (`client/src/App.tsx`).

## Knowledge Hub scope

All learning lives under `/knowledge`. `client/src/lib/scope.ts` holds the pure rules (`scopeFor`, `inScope`, `frameworksFor`, `scopeName`). `useHubScope()` in `client/src/lib/hubScope.ts` returns the scope pages filter by. With a selected entity (remembered in `rch.entity`, set when its dashboard opens, ignored if it belongs to another workspace, cleared on sign-out and on switching workspace) the hub shows that entity's jurisdiction plus international content, and "Show all jurisdictions" turns the filter off for the tab session (`rch.hubShowAll`). With no entity the hub is unfiltered and `ScopeBanner` offers an All / Australia / UK switch (`rch.hubScope`). Storage access goes through `client/src/lib/stored.ts`, which wraps every call in try/catch.

## Chat

Built in P3. **Not checked against a live provider:** no test or check has called Anthropic or Gemini; the owner's live check is owed.

- **Where:** `ChatPanel` (the hub overview, signed-in only, and the entity dashboard) uses `client/src/lib/chat.ts` to list, create, rename and delete conversations and to stream a message. A conversation belongs to an entity (`client_id`) or, in the hub, to a scope (`AU`, `UK`, `ALL`); the database requires exactly one of the two.
- **Flow** (`chatService.runExchange`, behind `POST /api/conversations/:id/messages`): check the guard (see "Spend guard") and that a provider is configured; save the user's message; redact the question, the account names, the history and any attached documents with the conversation's map (`redactWith`), using the workspace's client names; build the search query from the redacted question; embed it if an embedder is set; `searchKbForChat` (published versions only, jurisdiction from the entity or scope, Bills included and labelled); `isCovered` decides, and a question the knowledge base doesn't cover gets the fixed "not covered" reply **without a provider call**; otherwise send the sources and `buildPrompt` to the provider (attached documents go in a `<documents>` block before `<sources>`, labelled D1, D2; they are context, never a source, and a number found only in a document is flagged `from_document`), stream the answer, run `checkGrounding`, save the message with its citations, and record usage. No database transaction is open while the embedder or provider runs.
- **SSE events:** `start` (the saved user message), `sources` (the numbered citations), `delta` (text), `done` (the saved assistant message) and `error`. A client that disconnects aborts the provider call.
- **Statuses** of a message: `sent` (user), then `answered`, `flagged` (a grounding flag was raised and the answer is shown labelled), `not_covered`, `refused` (the provider refused), `stopped` and `error`.
- **The `[n]` scheme:** both providers get the same numbered sources and the same system prompt (`server/src/chat/prompt.ts`) and cite as `[n]`. Anthropic's native `search_result` citations are not used, so one grounding check serves both. Citations are copied into `chat_citation` as a snapshot (no foreign keys), because a fact edit re-chunks published guides.
- **Grounding** (`checkGrounding`): an answer is flagged `uncited` (no marker, or a long block with none), `bad_marker` (a marker no source carries) `unsupported_number` (a figure in neither a cited source nor a fact value) or `from_document` (a figure that is only in an attached document). It checks that a number appears in the cited text, not that the model reasoned correctly; flagged answers are labelled, not hidden.
- **Retrieval:** `searchKbForChat` in `server/src/kb/retrieve.ts` ORs the question's lexemes, because `websearch_to_tsquery` ANDs every word and would call almost every natural question "not covered" while `GEMINI_API_KEY` is unset. `searchKb` (the admin search) is unchanged.
- **Coverage constants** `MIN_LEXEME_COVERAGE_BP = 5000` and `MIN_SIMILARITY_BP = 6000` in `server/src/chat/coverage.ts` are **untuned guesses**, not tested against real questions.
- **Providers:** `CHAT_PROVIDER` picks `anthropic` (the default, `@anthropic-ai/sdk`) or `gemini` (plain `fetch` to `streamGenerateContent`; tested against a stubbed `fetch` only). Gemini chat has **no price row** in `pricing.ts`, so it cannot be configured until one is added with a source.

### PII redaction

`redact()` (`server/src/privacy/redact.ts`) replaces, in a fixed order, the workspace's client names, emails, IBANs, card numbers that pass the Luhn check, AU and UK bank accounts, AU and UK phone numbers, ABN, UTR, TFN or ACN, and UK National Insurance numbers with typed placeholders (`[EMAIL_1]`, `[NAME_2]`). Placeholders are numbered per call, so the same string reuses one within a call. Rules only: a name that is not in the workspace's client list (a director, an employee) is not caught, and the NI pattern and the nine-digit patterns deliberately over-redact. Since P4 every conversation keeps one placeholder map (`redactWith` continues numbering from it, so `[NAME_1]` means the same thing in every turn and in every attached document). The map is stored in `conversation.redaction_map`, sealed with AES-256-GCM (`server/src/privacy/crypto.ts`, AAD `conversation:<org>:<id>`), and is read and written only through `withRedactionMap`, one short `withOrg` transaction with a row lock that commits before any embedder or provider call. Answers are stored and graded with their placeholders; they are restored to real values only in responses to a signed-in member of the firm (the stream through `createRestorer`, and `GET /api/conversations/:id` through `restoreMessageView`). The user's own message body is stored raw, as in P3. A named-entity pass for names that are not in the client list is still owed (NER). The model is told to keep placeholders as they are. Logs never hold a message body.

### Spend guard

A minimal guard, not the P5 rate limiter. Every provider call writes one row to `ai_usage` (tokens and `cost_micro_usd`, no text) through `usageService`. Before a call, `checkGuard` refuses when today's (UTC) global cost has reached `DAILY_SPEND_CAP_USD` or this user's calls today have reached `CHAT_DAILY_MESSAGES_PER_USER` (429). The limit counts provider calls, so "not covered" answers are free and errors still count. Cost is integer micro-USD through `roundDiv` from `PRICES`; a model not in `PRICES` is charged at the highest tier. `PRICES` was read from Anthropic's pricing page and Google's Gemini pricing page on 2026-10-28 (`PRICES_CHECKED_ON`). Cache reads are priced per model through `cacheReadFortieths` (0.05x input for Opus 5.5 and Sonnet 5.5, 0.1x for the others); Haiku 5.5 is priced at its >100k-token tier so a long prompt is never under-counted; `gemini-2.5-flash` ($0.30 in, $2.50 out per million tokens) is priced but Google no longer offers it to new users (404, 2026-10-30); `gemini-3.8-flash` (read 2026-10-30) is priced at the page's rate from 2027-01-01, $1.50 in and $7.50 out per million tokens, double the 2026 rate, so the guard never under-counts. Gemini bills thinking tokens as output, so `geminiChat` adds `thoughtsTokenCount` to the output tokens. Set `CHAT_PROVIDER=gemini` and `GEMINI_MODEL=gemini-3.8-flash` to use it. Since Stage 3 every Anthropic request carries `inference_geo` (`ANTHROPIC_INFERENCE_GEO`, default `us`), and `recordUsage` prices an Anthropic call at 1.1x every category when it is `us` (`costMicroUsd(model, u, { usOnly })`, integer arithmetic through `roundDiv`; Anthropic's data residency page, read 2026-10-31). Two simultaneous requests can both pass the guard; P5 owes real limits.

## Adding things

- **A topic**: a Markdown file in the right `docs/` section, plus its quiz questions and flashcards. The site picks it up automatically (skill: `topic-author`).

- **A tool**: engine + test in `client/src/utils/`, page in `client/src/pages/tools/`, a route in `App.tsx`, an entry in `client/src/content/tools.ts` (skill: `new-interactive`).
- **A data file**: schema in `schemas.ts`, parse in `index.ts`, cross-reference checks in `data.test.ts`.

## Database

Postgres 17 with pgvector runs in Docker Compose (`chub-db`, host port 5437). Two roles:

- `chub` owns the schema and runs migrations (`DATABASE_ADMIN_URL`, read only by `server/scripts/migrate.ts` and `drizzle.config.ts`).
- `chub_app` is what the server connects as (`DATABASE_URL`). It is `NOSUPERUSER NOBYPASSRLS` and owns nothing, because a superuser or table owner would bypass row-level security.

The tenant recipe (Hard rule 11): a tenant table has `org_id text not null`, `ENABLE` and `FORCE ROW LEVEL SECURITY`, and a policy on `current_setting('app.org_id', true)` (see `0003_client_rls.sql`, policy `client_isolation`). Every tenant query runs inside `withOrg(orgId, …)`, which sets `app.org_id` for the transaction, and still carries its own `org_id` predicate. Each tenant table needs a cross-tenant test.

Global tables (no `org_id`, no RLS, written only through `requireAdmin` routes and the seed script): `admin_audit` (append-only: `chub_app` has no `UPDATE` or `DELETE`, migration 0007) and the knowledge base, `kb_source` (an Act, Bill, ruling, standard or curriculum topic), `kb_version` (draft, published, superseded or withdrawn; `chub_app` cannot `DELETE` it, so versions are withdrawn, never deleted) and `kb_chunk` (a provision, with a generated `tsv` full-text column, a GIN index and a `vector(768)` embedding with an HNSW index; `chub_app` may `DELETE` chunks because a draft is re-chunked). Facts (P2b, migrations 0013 and 0014): `kb_fact` (key, label, jurisdiction, unit `bp`, `cents`, `count`, `date` or `text`, a numeric or text value, `effective_from`, `source`, `verified_on`, `note`, `updated_by`; checks on key shape, jurisdiction, unit and that the right value column is set; `chub_app` cannot `DELETE`) and `kb_fact_history` (one row per save with the whole fact, the change note and the actor; append-only: `chub_app` cannot `UPDATE` or `DELETE`). `kb_source.meta` (nullable jsonb, the curriculum frontmatter as `CurriculumMeta`) marks a curriculum source the public site may serve. Migration 0008 creates the `vector` extension as `chub`. `user_one_platform_admin` is a partial unique index allowing one `user.role = 'platform_admin'`; `kb_version_one_published` allows one published version per source. Versions are never edited once published: a change is a new version that supersedes the old one. Publish embeds first, then writes the embeddings and the status change in one transaction.

Tenant tables for the data track (D1, migrations 0011 and 0012, RLS forced, policies `ledger_import_isolation`, `ledger_account_isolation`, `ledger_balance_isolation`): `ledger_import` (one trial balance as at a date; at most one `active` per client and date, an earlier one becomes `superseded`), `ledger_account` (a client's accounts, unique by code, with `account_class` and whether the user set it) and `ledger_balance` (one debit or credit per account per import). Composite foreign keys on `(id, org_id)` mean a row cannot point at another firm's client, import or account. Amounts are integer cents. The uploaded file is not stored: only its SHA-256 and the parsed balances are.

Chat tables (P3, migrations 0015 and 0016, RLS forced, policies `conversation_isolation`, `chat_message_isolation`, `chat_citation_isolation`): `conversation` (an entity's or a hub scope's chat; check constraints tie `client_id` to `scope`), `chat_message` (role, status, grounding flags, provider and model; checks tie a user message to status `sent`) and `chat_citation` (a snapshot of each cited chunk, with no foreign keys to the KB; since P3b, migrations 0017 and 0018, a row with `kind: 'ledger'` cites a profit and loss or balance sheet instead, with null KB ids and `ledger_import_id`, `ledger_compare_import_id`, `ledger_report` and `ledger_as_at`; two checks make a row one or the other, and there is no foreign key to `ledger_import`, by design, so a citation outlives a deleted import). Composite foreign keys on `(id, org_id)` keep a chat inside its firm, and deleting a client deletes its chats. `ai_usage` is a **global** table (no RLS, no foreign keys, so spend history outlives a workspace): `chub_app` can insert but not update or delete it, and it holds no text. Token counts and cost live only there, not on `chat_message`.

Document tables (P4, migrations 0019 to 0021, RLS forced, policies `document_isolation`, `conversation_document_isolation`): `document` (an entity's uploaded file: `kind`, `byte_size`, `sha256`, `text_chars`, `truncated`, and the sealed `file_enc` and `text_enc`; unique on `(client_id, sha256)` so the same file is stored once; foreign key `(client_id, org_id)` to `client`) and `conversation_document` (which documents a chat has; primary key `(conversation_id, document_id)`). Both of its foreign keys are composite and carry `client_id` and `org_id`, so a document can only be attached to a chat of the same entity and firm. A hub chat has `client_id` null, which can never match a non-null column, so a hub chat cannot attach a document. `conversation` also gained `redaction_map bytea` (0019) and the unique constraint `conversation_id_client_org_unique`.

Request table (C2, migrations 0024 and 0025, RLS forced, policy `document_request_isolation`): `document_request` (one document to ask an entity for: `item_id`, `label`, `why`, `doc_id`, `source_url`, `verified_on`, `due_on`, `status` open, received or waived, `source` rule, manual or obligation, `obligation_id`; composite foreign key `(client_id, org_id)` to `client`; unique `(client_id, item_id, obligation_id)` with `NULLS NOT DISTINCT`, so generating twice adds nothing; checks on status, source, label length, and that an obligation request has an obligation id and a due date). Routes under `/api/clients/:clientId/requests`: `GET /`, `POST /generate`, `POST /`, `PATCH /:requestId`, `DELETE /:requestId` (owner or admin); another firm's ids answer 404. Generation reads the deadline facts from `kb_fact` on the server and looks 90 days ahead (`GENERATE_WINDOW_DAYS`, untuned).

Request link tables (C3, migrations 0034 and 0035, RLS forced, policies `request_link_isolation`, `request_link_item_isolation`): `request_link` (one private upload link: `client_id` by composite foreign key, `token_hash` (SHA-256, unique) and `token_enc` (the token sealed under `DATA_ENCRYPTION_KEY`, AAD `request_link.token:<org>:<id>`), `recipient_email`, `expires_at`, `revoked_at`, `paused`, `cadence_days integer[]`, `nudge_count`, `last_nudged_at`; checks on hash length, email length, cadence (at most 5 entries, each 1 to 89) and `nudge_count` 0 to 5) and `request_link_item` (the requests on a link, primary key `(link_id, request_id)`, composite foreign keys to the link and to `document_request`, which gained `unique (id, client_id, org_id)`). `document` gained `request_id`, `request_link_id` and `supersedes_id` (composite foreign keys, each `ON DELETE SET NULL` of the one column so deleting a request or link keeps the file; a link upload has `uploaded_by = 'client_link'`). The sealed `token_enc` exists because a reminder email must carry the link and a hash cannot be reversed; staff see the URL only in the create response, and key rotation (P5d) must re-seal it. `request_link_resolve(bytea)` is the project's only SECURITY DEFINER function: an anonymous client has no `app.org_id` yet, so it looks up a live (not revoked, not expired) link by token hash and returns `org_id`, `client_id` and `link_id` and nothing else; it is owned by `chub`, has `search_path` pinned to `pg_catalog, public`, and `EXECUTE` goes to `chub_app` only. Every query after it runs in `withOrg`. Public routes `/api/public/requests/:token` (view) and `.../items/:requestId/upload` sit outside `requireFirm`, rate limited per IP before the body is read, answer one 404 for every bad token and send `Cache-Control: no-store`. The web page `/r/:token` is a route outside `Layout`. The reminder job `server/src/jobs/nudges.ts` (advisory lock 5001302, first tick 90 s after start, then every 10 minutes) mails outside any transaction and updates `nudge_count` only if it is unchanged. New limits (`LIMITS`, untuned): `publicView` 120 per hour per IP, `publicUpload` 20 per hour per IP, `requestLink` 30 per hour per user.

Engagement tables (W1, migrations 0026 and 0027, RLS forced, policies `engagement_template_isolation`, `engagement_isolation`, `task_isolation`): `engagement_template` (a firm's copy of a seed: name, kind, steps), `engagement` (belongs to one client by composite foreign key; `template_id` is text, `seed:<id>` or `firm:<uuid>`, with no foreign key because tasks are copied at creation; unique `(client_id, obligation_id)` so opening is idempotent), `task` (ordered by position; assignee references `user` with `ON DELETE SET NULL` and must be a member of the same firm; `done_at` is set exactly when the status is done). `client.auto_engagements` is set by `PATCH /api/clients/:clientId/engagements/auto`. Routes: `/api/engagements` (list, members, get, patch, delete for owner or admin, tasks add, patch, move, delete), `/api/engagement-templates` (list, copy from a seed, get, patch, delete for owner or admin) and `/api/clients/:clientId/engagements` (list, create, `/auto`, `/open` over a 90-day window, `OPEN_WINDOW_DAYS`, untuned). Pages: `/engagements`, `/engagements/:id`, `/entities/:id/engagements`, `/workspace/templates`, `/workspace/templates/:id`. No provider is called and no text is logged.

Audit and retention (P5c, migrations 0032 and 0033): `audit_event` is a tenant table (`id bigserial`, `org_id` with a cascading foreign key, `actor_id` with no foreign key so a reference outlives a deleted user, `action`, `target_type`, `target_id`, `ip_key`, `detail jsonb`, `created_at`; index `audit_event_org_id_idx (org_id, id)`; forced RLS, policy `audit_event_isolation`). It is append-only by `REVOKE UPDATE, DELETE ON "audit_event" FROM chub_app` in 0033 (0001's default privileges grant both to every new table), so `chub_app` holds INSERT and SELECT only. `audit_event_action_check` lists 11 actions (`sign_in`, `document.upload`, `document.download`, `document.delete`, `ledger.import`, `ledger.delete`, `member.invite`, `member.remove`, `member.role`, `retention.update`, `retention.purge`) and `audit_event_target_type_check` six targets (`user`, `document`, `ledger_import`, `invitation`, `member`, `organization`). `detail` holds ids, counts and role names only, never a file name, an email, a message or upload text, and the raw IP is never stored (`ip_key` is the HMAC from `ipKey`). It is not `admin_audit`, which stays global and unchanged (`auditService.ts`). The tenant log is written by `server/src/services/auditEventService.ts` (`recordEvent(tx, …)` inside the action's own `withOrg` for document upload, download and delete and for trial-balance import and delete; `recordEventForOrg` in its own `withOrg` for the rest) and, for sign-in and member invite, remove and role change, by `server/src/services/authAudit.ts`, a Better Auth `hooks.after` middleware that runs after Better Auth commits and logs only `('audit', { action, ok: false })` on failure; `sign_in` is a successful `POST /sign-in/email` and writes one event per workspace the user belongs to. The actor in that hook is read with `getSessionFromCtx(ctx)` because `ctx.context.session` was empty in the after-hook. `organization` gained `retention_days_documents` and `retention_days_conversations` (hand-added, nullable, `organization_retention_days_check` allows null or 30 to 3650; written only by `PATCH /api/workspace/retention`, which also writes a `retention.update` event). Routes: `GET /api/audit?before=&limit=` (owner or admin, else 403; limit 1 to 100, default 50; newest first; never returns `ip_key`), `GET /api/workspace/retention` (any role; returns `canEdit`) and `PATCH /api/workspace/retention` (owner only). The job in `server/src/jobs/retention.ts` starts from `server/src/index.ts` only: first tick 60 s after start, then every 6 hours; a tick takes a session-level advisory lock (`pg_try_advisory_lock(5001301)`) on one pooled connection so one API instance purges at a time, deletes each firm's documents older than its setting (by `document.created_at`) and conversations (by `conversation.updated_at`; the redaction map goes with the row) inside that firm's `withOrg`, writes one `retention.purge` event (`actorId` null, counts only) for a firm that lost rows, then deletes `rate_bucket` rows older than a day. Both settings start null (keep forever). Deleted `bytea` space is reclaimed by `server/scripts/vacuum.ts` (`npm run db:vacuum -w server`), which runs `VACUUM (ANALYZE)` on `document` and `conversation` as the owner role through `DATABASE_ADMIN_URL`; the app never runs it and P5d schedules it. The page is `/workspace/audit` (the audit table for owners and admins; the retention form for the owner, read-only for others). No new dependency and no new env var.

Workload tables (W2, migrations 0030 and 0031): `member_capacity` (tenant table, primary key `(org_id, user_id)`, `weekly_minutes` 0 to 6000, RLS forced, policy `member_capacity_isolation`; membership is checked in the service, not by a foreign key, so a row left by a member who leaves is ignored) and `organization.timezone` (hand-added to Better Auth's table, nullable, `organization_timezone_check` against the eight `CALENDAR_TIMEZONES`, written only by `PATCH /api/workload/timezone`, not a Better Auth field). Routes: `GET /api/workload[?week=yyyy-mm-dd]` (any role; the week must be a Monday, else 400), `PATCH /api/workload/timezone` and `PATCH /api/workload/capacity/:userId` (owner or admin; PATCH, not PUT, because CORS allows no PUT). Counting rules: weeks run Monday to Sunday in the firm timezone; a task counts when it is not done, its engagement is not done, it has an assignee who is a current member, and its due date (the task's, else the engagement's) is on or before the end of next week; earlier than this week is overdue, and overdue minutes add to this week's load but not next week's; a task with no estimate counts 0 minutes and adds 1 to the no-estimate count; capacity 0 gives no load. Rows come back in member order and are never ranked. Until the timezone is set, `/workload` asks an owner or admin to set it. No provider is called and no text is logged.

Tables today: `client` (tenant table), `audit_event` (P5c, tenant table, append-only), the three ledger tables, the three chat tables, `document` and `conversation_document`, `document_request`, `request_link` and `request_link_item` (C3), `ai_usage`, `rate_bucket` (global, no RLS and no `withOrg` by design: per-IP (HMAC'd, never raw) and per-user rate-limit counters, one atomic upsert in `rateLimitService.consume`; migrations 0028 and 0029; the proxy rule is that `pinForwardedFor` overwrites `x-forwarded-for` with `req.ip`, which honours `TRUST_PROXY_HOPS`, before Better Auth reads it), the global tables above, plus Better Auth's seven (`user`, `session`, `account`, `verification`, `organization`, `member`, `invitation`). A workspace is a Better Auth organization with `kind` (`business` or `practice`, set at create, immutable via `beforeUpdateOrganization`); roles are owner, admin, member. A business holds exactly one `client` row with `is_self` (partial unique index `client_one_self_per_org`); a practice holds many. `client` profile columns: `entity_type`, `tax_registered`, `tax_period`, `fy_end_month`, with checks in `0005_workspace_checks.sql`. Migrations are append-only (Hard rule 14); a change is a new migration. Email (P5b): verification follows `REQUIRE_EMAIL_VERIFICATION`; reset and verification links are built by Better Auth and point at the API, which redirects to the web; Better Auth's `/send-verification-email` shares the password-reset rate limit (3 per hour per IP). The only sender is `server/src/mail/mailer.ts` (templates in `templates.ts`, plain text only); it logs template, recipient domain and outcome, never a body, link, token or address. Development mail goes to Mailpit (`mail` Compose service, container `chub-mail`, image `axllent/mailpit:v1.31.5`, SMTP on host port 5438, web UI on 5439). Web pages and routes: `/forgot-password`, `/reset-password`, `/check-email`, `/accept-invitation/:id`, `/workspace/members`.

## Facts and guides in the database

- **Source of truth:** `kb_fact` for facts; for guides, the published `kb_version` of a curriculum `kb_source` with `meta` set. `facts.json` and `docs/` are seeds (`kb:seed-facts`, then `kb:seed-curriculum`); the web bundle contains neither, and `client/scripts/check-bundle-content.mjs` (run by `npm run build` after the secret check) fails if `dist/` holds `{{fact:` or fact text.
- **Curriculum body:** stored as the frontmatter-stripped Markdown with its `{{fact:key}}` tokens kept and no `# title` line (the chunk `context` still carries `Compliance Hub guide: <title>`). Chunks hold the value rendered from `kb_fact` (`10%`, or `10% (unverified)`); an unknown key renders `[unknown fact <key>]` and blocks publish (`unknown_fact`).
- **A fact save** (`factService.writeFactInTx`, one transaction): lock and upsert the fact row, insert the history row, re-chunk every published and draft curriculum version whose body has the token or whose `meta.facts` lists the key (superseded and withdrawn versions are never touched; embeddings are cleared), write the audit row. Embedding runs after the commit and only when an embedder is configured; otherwise the admin is told the embeddings are missing until Embed missing runs. The server computes `verifiedOn`.
- **Import cycle:** `server/src/kb/curriculum.ts` and `server/src/services/kbService.ts` import each other. It works because neither uses the other at module load; keep it that way, or move the shared helpers into a third file.
- **Public API (no session):** `GET /api/kb/site` returns `{ facts, docs }` (ETag-aware); `GET /api/kb/laws?jurisdiction=&kind=` and `GET /api/kb/laws/:id` return published Acts, regulations, Bills, rulings and standards. Every query joins `kb_version` on `status = 'published'`.
- **Web flow:** `KbGate` wraps the routes in `App.tsx`. On mount `loadKb()` (`client/src/lib/kbStore.ts`) fetches `/kb/site`, zod-parses it, then calls `setFacts` and `setDocs`; pages read the registries inside components, never at module load. A failure shows an error with a Try again button, with no fallback numbers. Tests fill the registries in `client/src/__tests__/setup.ts` from `client/src/__tests__/seedData.ts`.

Read-only and small (fflate, saxen, unzipper-esm, worker-f) compared with exceljs, which brings archiver, tmp and fast-csv. 9.3.13 was skipped as under two weeks old on 2026-10-28 |

The server shares the root `vitest` (npm puts the root `node_modules/.bin` on the script path) and runs Better Auth's schema generator through `npx auth@1.7.13` instead of installing `vitest` or a CLI in `server/`: both crash npm 10.9.8's arborist (`Cannot read properties of null (reading 'edgesOut')`).

## Outbound hosts

The server calls out to only four kinds of host, and no test does (Hard rule 15).

- **Gemini embeddings:** `https://generativelanguage.googleapis.com/v1beta/models/<GEMINI_EMBED_MODEL>:batchEmbedContents`, with the key in the `x-goog-api-key` header and 768 dimensions. It receives published knowledge-base text and the platform admin's test-search queries, both public or admin-authored, so `redact()` does not apply (CLAUDE.md Hard rule 13). The request shape is taken from Google's public documentation and has not been checked against a live call.
- **Anthropic chat:** `api.anthropic.com`, through `@anthropic-ai/sdk`. It receives redacted questions, redacted history, redacted text of any attached documents and published knowledge-base text, never an unredacted question. Not checked against a live call.
- **Gemini chat:** the `streamGenerateContent` endpoint under `generativelanguage.googleapis.com`, plain `fetch`, same payload rules (so it also receives only redacted document text). The request and stream shapes come from Google's public documentation and have not been checked against a live call.
- **Official sites,** fetched by the admin's "fetch from URL" input: an `https` URL whose host equals or is a subdomain of one of `OFFICIAL_HOSTS` in `server/src/kb/officialSites.ts` (`legislation.gov.au`, `ato.gov.au`, `asic.gov.au`, `aph.gov.au`, `aasb.gov.au`, `treasury.gov.au`, `gov.uk`, `parliament.uk`, `frc.org.uk`, `ifrs.org`). Every redirect is checked against the same list, and a page over 10 MB is refused.

## Documents (P4)

Built in P4. **Not checked against a live provider or with a real client's files:** the owner's live check is owed.

- **Where:** `/entities/:id/documents` lists, uploads, downloads and deletes an entity's files (PDF, Word `.docx`, Excel `.xlsx`, CSV, text, Markdown). Routes: `GET`/`POST /api/clients/:clientId/documents`, `GET .../:docId/file`, `DELETE .../:docId`. Upload, list, download and attach are open to owners, admins and members; delete is for owners and admins (a member gets 403). In an entity chat, `POST` and `DELETE /api/conversations/:id/documents` attach and detach.
- **Tables:** `document` and `conversation_document` (see "Database" for the keys, and why a hub chat cannot attach a document).
- **Sealed at rest:** the original bytes go to `file_enc` and the extracted text to `text_enc`, each sealed with AES-256-GCM (`[version 1][iv 12][tag 16][ciphertext]`) under `DATA_ENCRYPTION_KEY`, with the AAD `document.file:<org>:<id>` or `document.text:<org>:<id>` so a ciphertext cannot be moved to another row or firm. List and view queries name their columns and never select either column. Sealing and extraction run outside any transaction.
- **Checks on upload:** the extension picks the kind, then the bytes must match it (a `%PDF-` header, a zip header, or valid UTF-8 without NUL for text kinds), then a zip central-directory walk rejects a `.docx` or `.xlsx` that claims more than 100 MB uncompressed, without inflating it. The body is read raw up to 20 MB. A duplicate (same SHA-256 for the entity) returns the stored document.
- **Limits (all untuned guesses):** `MAX_DOCUMENT_BYTES` 20 MB, `MAX_DOCUMENT_TEXT_CHARS` 400,000, `MAX_XLSX_CELLS` 200,000, `MAX_ZIP_UNCOMPRESSED_BYTES` 100 MB, `MAX_DOCUMENTS_PER_CLIENT` 200 and `MAX_DOCUMENT_CHARS_IN_PROMPT` 60,000.
- **In the chat:** attached documents are opened in their own short transaction, redacted with the conversation's map (name and text), and sent in `<documents>`. They are never embedded, never searched, never used to decide whether a question is covered, never cited, and the prompt says their instructions are not to be followed. Pdf extraction is given a plain `Uint8Array` because pdf.js rejects a Node `Buffer`.
- **Caveat:** redaction is rules plus the workspace's client names. A document full of staff or director names sends those names to the provider. The page says so; a named-entity pass is owed.
- **Storage:** documents live in Postgres. Deleted `bytea` space returns only after `VACUUM` (`npm run db:vacuum -w server`, scheduled by host cron, see `engineering/operations.md`); retention (P5c) deletes the rows. Losing `DATA_ENCRYPTION_KEY` makes every document and every conversation map unreadable, and key rotation is built in P5d (`npm run db:reseal -w server`; see Deploy shape), so back the key up separately from the database.
- **Dependency:** `read-excel-file` 9.3.12 reads `.xlsx` (reason in "Server dependencies and why"). `npm audit --omit=dev` after the install on 2026-10-28 reported 9 vulnerabilities (6 moderate, 3 high), all in the existing dev tooling (`@vitest/mocker`, `esbuild`, `nanoid`) and none in `read-excel-file` or its packages.

## Deploy shape (P5d)

- **Image:** `server/Dockerfile`, built from the repo root (`docker build -f server/Dockerfile -t compliance-hub-api:local .`), base `node:22.23.2-bookworm-slim`. The `build` stage runs `npm ci` and `npm run build -w client` (typecheck, Vite and both bundle checks). The `runtime` stage runs `npm ci --omit=dev --ignore-scripts` (the owner approved `--ignore-scripts`: with `--omit=dev` npm still installs drizzle-kit's nested `esbuild@0.18.20`, whose install script fails with `Expected "0.18.20" but got "0.28.2"`; the only install scripts in the lockfile are the esbuild copies and `fsevents`, and tsx runs from the `@esbuild/<platform>` binary without the script), then copies `shared/`, `server/`, `docs/` and the built `client/dist`, and runs as the `node` user (uid 1000). `.dockerignore` keeps `.env*`, `.git`, `backups`, tests and plans out. No secret is in an `ENV` or `ARG`; settings come from `env_file` at run time.
- **Static serving:** `server/src/app.ts` mounts, last and only when `WEB_DIST_DIR` is set, `express.static` (no index) and a GET fallback to `index.html`. Files under `assets/` get `Cache-Control: public, max-age=31536000, immutable`; `index.html` and the fallback get `no-cache`; every static response carries `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` (so a `/r/:token` URL never reaches the font host). `/api/*` never falls through to `index.html`.
- **Compose:** `db` (port published on `127.0.0.1:5437` only; password `${POSTGRES_PASSWORD:-chub}`) serves dev and prod. `mail` has `profiles: [dev]` (`./dev.sh` names it). With `--profile prod`: `migrate` (migrations and both seeds, then exits; gets `.env.production` and `.env.production.admin`) and `api` (container `chub-api`, `127.0.0.1:5191`, gets only `.env.production`, never the owner credentials). Committed templates: `.env.production.example`, `.env.production.admin.example`; the real files are git-ignored.
- **`scripts/`:** `backup.sh` (`pg_dump -Fc` inside `chub-db`, `.partial` then rename, default folder `backups/`, ignored) and `restore-drill.sh` (restores into `chub_restore_drill`, runs `server/scripts/drill-check.ts` in the image: counts, migrations, and opens up to five sealed rows of each kind with the configured key). The runbook is `engineering/operations.md`.
- **Keyring and re-seal:** a sealed value is `[key version (1 byte)][iv 12][tag 16][ciphertext]`. `server/src/privacy/crypto.ts` has `Keyring { current, previous | null }`, `envKeyring()` (from `DATA_ENCRYPTION_KEY_VERSION` and `DATA_ENCRYPTION_KEY_PREVIOUS`) and `sealVersion`; `seal` writes the current version, `unseal` opens only the two versions in the ring. `resealAll` in `server/src/jobs/reseal.ts` (`npm run db:reseal -w server`) rewrites every sealed column (`document.file_enc`, `document.text_enc`, `conversation.redaction_map`, `request_link.token_enc`) whose version byte is not current, firm by firm in `withOrg` with the `org_id` predicate, in batches of 100, each update conditional on the old ciphertext, so it can be re-run. A row that opens with neither key stops the run with `Cannot open <table> <id>` and no content.

## Stage 3 launch gate

- **Region.** One deployment per country. `DEPLOYMENT_REGION` (`AU` or `UK`) is required in production; `GET /api/meta` (`server/src/routes/meta.ts`, public, no database) returns `{ region, otherRegionUrl, legalVersion }`, which the web reads once through `client/src/lib/deployment.ts` (`loadDeployment`, `useDeployment`). The shared constants and schema are in `shared/src/lib/legal.ts` (`LEGAL_VERSION`, `LEGAL_DOCS`, `REGION_LABEL`, `deploymentInfoSchema`).
- **Legal pages.** `/legal/privacy`, `/legal/terms`, `/legal/processing` and `/legal/subprocessors` (`client/src/pages/legal/LegalPage.tsx`) render the region's Markdown from `client/src/content/legal/{au,uk}/` (raw imports), under a "Draft: needs legal review" banner, and are linked from the footer. Each draft carries `[Owner: ...]` and `[To be confirmed: ...]` placeholders; the sources behind them are in `engineering/legal-sources.md`. Changing any page means changing `LEGAL_VERSION`.
- **Terms acceptance.** Sign-up sends `termsVersion`; Better Auth's `user.additionalFields.termsVersion` is required, and a `databaseHooks.user.create.before` hook in `server/src/auth.ts` refuses any version other than `LEGAL_VERSION` (400, "Accept the current terms of service and privacy notice to create an account.") and sets `termsAcceptedAt` on the server (`input: false`). Migration 0036 adds the two nullable columns; accounts made earlier have none.
- **Redaction warning.** `client/src/components/RedactionNotice.tsx` (variants `documents`, `chat`, `client-upload`) states what `redact()` replaces and that other names are not caught; it shows on the entity Documents page, above the chat form and on the client's public upload page.

## Theming

Light by default; dark from the system preference unless forced. `client/index.html` applies the saved choice before first paint; `ThemeToggle` in `Layout.tsx` is the only other writer of `rch.theme`. Colours are CSS variables mapped to Tailwind names (`bg-panel`, `text-muted`, `bg-accent-soft`…) in `client/src/index.css`. Never use a raw colour class.
